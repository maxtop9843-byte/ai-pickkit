# Pickkit Canonical Design Guide

이 문서는 Pickkit의 모든 화면 추가·수정 작업에서 사용하는 저장소 내부의 최우선 디자인 기준이다.

Pickkit은 AI 비용과 모델 선택을 빠르게 판단하는 도구다. 디자인은 **Hyperstudio의 편집적 테크 무드**, **Raycast의 정교한 도구 인터페이스**, **Apple의 절제된 라이트 모드와 여백 원칙**을 Pickkit의 제품 목적에 맞게 재구성한다. 어느 브랜드도 그대로 복제하지 않는다.

## 1. 핵심 디자인 방향

Pickkit의 최종 인상은 다음 한 문장으로 정의한다.

> 미래적인 AI 브랜드 무드 위에, 냉정하고 신뢰할 수 있는 비용 의사결정 도구를 얹는다.

- 홈과 브랜드 영역은 실험적이고 기억에 남을 수 있다.
- 계산기, 비교표, 입력, 결과 영역은 명료하고 안정적이어야 한다.
- 다크 모드와 라이트 모드는 색상 반전판이 아니라 동일한 정보 계층을 공유하는 두 개의 완성된 테마다.
- 장식은 입력, 비교, 결과, 출처, 다음 행동을 방해하지 않는다.
- 새 기능은 기존 화면과 같은 제품에서 나온 것처럼 보여야 한다.
- 기능마다 별도의 시각 언어를 만들지 않는다.

## 2. 레퍼런스 역할

### Hyperstudio에서 채택

- 큰 면적의 중성 캔버스와 1px hairline 구조
- 장식보다 타이포그래피, 선, 점, 여백으로 만드는 AI·테크 분위기
- 낮은 카드 반경과 절제된 표면
- 홈 히어로의 도트 매트릭스·도트 필드 비주얼
- 무거운 그림자 없이 경계와 대비로 만드는 깊이
- 굵기보다 크기와 간격으로 만드는 조용한 헤드라인

### Raycast에서 채택

- 어두운 도구 인터페이스의 높은 완성도와 정보 밀도
- 입력 well, 키 캡처럼 촉각적인 선택 상태, hairline 강조
- Inter/Geist 계열의 명료한 인터페이스 타이포그래피
- 기능적 UI는 대부분 무채색으로 유지하고 신호색을 제한적으로 사용
- 결과, 상태, 메타데이터에 모노스페이스를 제한적으로 사용
- hover, press, focus 상태가 작지만 명확하게 느껴지는 인터랙션

### Apple에서 제한적으로 채택

- 라이트 모드의 따뜻한 fog canvas와 순백색 표면 계층
- 넓은 여백, 명확한 문장 계층, 불필요한 장식 제거
- 그림자보다 표면색 차이로 만드는 깊이
- 핵심 전환 행동에만 선명한 강조색 사용
- 제품 시각물과 문구에 숨 쉴 공간을 주는 구성

다음 Apple 요소는 Pickkit에 기본 적용하지 않는다.

- 72~96px의 제품 광고형 대형 헤드라인
- 모든 버튼과 컨테이너의 과도한 pill·28px 반경
- 계산 도구보다 제품 이미지가 우선하는 갤러리형 레이아웃
- 정보 밀도를 지나치게 낮추는 대형 공백

## 3. 제품 인상

- AI스럽지만 유행 템플릿처럼 보이지 않는다.
- 전문적이되 차갑지 않다.
- 정보 밀도는 높지만 읽기 흐름은 명확하다.
- 데이터와 계산 결과가 장식보다 먼저 보인다.
- 신뢰감, 속도감, 정밀함을 동시에 전달한다.
- 마케팅 영역과 제품 영역의 분위기는 연결되지만 밀도는 다르게 설계한다.

## 4. 피해야 할 표현

- 흔한 보라색 또는 무지개 그라데이션
- 의미 없는 대형 영웅 문구
- 모든 요소를 둥근 카드로 감싸는 구성
- 불필요한 유리 효과와 과도한 그림자
- 장식용 3D 오브젝트와 제품과 무관한 일러스트
- 복제형 AI SaaS 대시보드
- 정보 계층 없이 동일한 강도로 반복되는 카드
- 계산기보다 더 눈에 띄는 애니메이션
- 상시 움직이는 입자, 커서 추적 효과, 과도한 glow
- 모바일에서 표와 입력이 잘리는 구성
- 다크 모드만 멋있고 라이트 모드는 단순 반전처럼 보이는 구현

## 5. 테마 시스템

### 공통 원칙

- 모든 색은 역할 기반 토큰으로 관리한다.
- 컴포넌트에서 직접 색상 값을 반복하지 않는다.
- 다크·라이트 테마의 대비, 위계, 상태 의미는 동일해야 한다.
- 테마 전환 시 레이아웃과 이미지 크기가 움직이지 않아야 한다.
- 시스템 설정을 기본으로 따르고 사용자의 명시적 선택을 저장한다.
- 새로고침 시 테마 깜빡임을 방지한다.

### 다크 모드

- Canvas: `#0b0c0e` 전후의 따뜻한 near-black
- Surface: canvas보다 한 단계 밝은 중성 검정
- Recessed input: surface보다 낮고 분명한 입력 well
- Primary text: 순백색보다 약간 부드러운 off-white
- Secondary text: 충분한 대비를 갖는 중성 회색
- Border: 1px hairline, 배경과 구분되지만 밝게 튀지 않음

### 라이트 모드

- Canvas: Apple의 fog canvas에서 가져온 `#f5f5f7` 계열
- Surface: `#ffffff`
- Recessed input: 옅은 중성 회색
- Primary text: 순수 검정보다 부드러운 warm ink
- Secondary text: WCAG 대비를 충족하는 중성 회색
- Border: 표면을 구분하는 옅은 hairline

### 신호색

- 브랜드 신호색은 한 계열만 사용한다.
- CTA, 현재 선택, 핵심 결과, 활성 상태에만 제한한다.
- 성공, 경고, 오류는 의미가 있을 때만 별도 색상을 사용한다.
- 다크·라이트 모두에서 같은 의미와 충분한 대비를 유지한다.
- coral 계열은 브랜드 punctuation 후보로 사용할 수 있으나 일반 본문 링크와 모든 아이콘에 확산하지 않는다.

## 6. 도트 비주얼 시스템

도트는 Pickkit의 대표 브랜드 모티프다. AI, 모델 공간, 계산 노드, 데이터 밀도를 암시하되 장식 소음이 되지 않아야 한다.

### 기본 동작

- 다크 모드: 어두운 캔버스 위 off-white 도트
- 라이트 모드: 밝은 캔버스 위 ink 도트
- 테마 전환 시 도트 색상이 자연스럽게 반전된다.
- 도트의 위치와 밀도는 유지해 레이아웃 점프를 방지한다.
- CSS mask, radial-gradient, SVG 또는 canvas 중 성능과 접근성이 가장 나은 방식을 선택한다.
- 실제 콘텐츠 텍스트와 겹치는 구간은 mask 또는 낮은 opacity로 읽기 대비를 확보한다.

### 허용 범위

- 홈 히어로 배경 또는 대표 비주얼
- 로딩·빈 상태의 제한적인 그래픽
- 기능 카테고리 간 연결을 암시하는 작은 노드 패턴
- 모델 비교나 비용 흐름을 설명하는 데이터 시각화

### 금지 범위

- 전체 페이지에서 계속 움직이는 파티클
- 포인터를 과도하게 추적하는 효과
- 입력·결과 영역 뒤에서 읽기를 방해하는 고밀도 패턴
- 성능 저하를 유발하는 대형 canvas 애니메이션
- 도트만으로 상태나 정보를 전달하는 구성

## 7. 타이포그래피

- 기본 인터페이스 서체는 Inter, Geist 또는 높은 가독성의 system-ui를 사용한다.
- 홈 히어로는 400~500 굵기의 큰 제목을 사용할 수 있지만 모바일에서 과장되지 않게 축소한다.
- 도구 페이지 제목은 500~600을 기본으로 한다.
- 700~900 굵기를 반복적으로 사용하지 않는다.
- 본문은 16~17px, 줄높이 1.45~1.6을 기본으로 한다.
- 숫자, 가격, 토큰, 코드, 모델 ID, 검증일은 Geist Mono 같은 모노스페이스를 제한적으로 사용한다.
- 숫자는 가능하면 tabular numbers를 사용해 값 변경 시 흔들림을 줄인다.
- 제목 크기보다 정보 구조와 간격으로 위계를 만든다.

## 8. 간격, 모서리, 깊이

- 4px 기반 척도와 8px 리듬을 사용한다.
- 카드 내부 기본 여백은 20~24px, 복잡한 비교 패널은 24~32px다.
- 마케팅 섹션 간격은 80~120px, 도구 화면은 더 촘촘하게 구성한다.
- 입력, 버튼, 작은 패널의 기본 반경은 8px다.
- 큰 카드와 결과 패널은 10~12px를 기본으로 하며 16px를 넘기지 않는다.
- pill은 주요 CTA, 필터, 상태 chip, 명확한 선택 컨트롤에만 사용한다.
- 그림자는 기본값이 아니다.
- 깊이는 1px hairline, 표면색 변화, inset highlight, 간격으로 만든다.
- Raycast식 key surface는 선택·프리셋·도구 카드에 제한적으로 사용한다.
- 깊은 그림자와 glow는 히어로 비주얼이나 특별한 부유 요소에만 제한한다.

## 9. 정보 구조와 레이아웃

### 홈

홈은 단순 도구 목록이 아니라 사용자의 목적 선택 화면이어야 한다.

- AI 기능의 월 비용 계산
- 사용자 한 명당 원가 확인
- 더 저렴한 모델 찾기
- 예산에 맞는 모델 조합 설계
- 요금제와 마진 계산

첫 화면에서 다음을 동시에 이해할 수 있어야 한다.

1. Pickkit이 무엇을 해결하는지
2. 어떤 입력을 하면 어떤 결과를 얻는지
3. 주요 도구로 어떻게 진입하는지
4. 전체 도구를 어디서 찾는지

### 도구 화면

핵심 도구는 다음 순서로 읽혀야 한다.

`입력 → 계산 또는 비교 → 결과 → 비용 구성과 해석 → 근거와 출처 → 공유·저장·내보내기`

- 데스크톱에서는 입력과 결과를 나란히 둘 수 있다.
- 모바일에서는 단일 열로 자연스럽게 이어져야 한다.
- 결과는 페이지 하단에 숨기지 않고 입력 변화와 함께 즉시 이해되도록 배치한다.
- 고급 옵션은 disclosure로 접되 계산에 영향을 주는 숨은 기본값을 만들지 않는다.
- 비교 테이블은 첫 열과 헤더의 맥락을 유지한다.
- 긴 설명은 도구를 밀어내지 않도록 요약과 상세를 분리한다.

## 10. 컴포넌트 규칙

### 버튼

- 주요 행동은 한 화면에 하나의 시각적 우선순위를 갖는다.
- 버튼 최소 높이는 데스크톱 40px, 모바일 44px다.
- hover, active, focus-visible, disabled, loading 상태를 구현한다.
- 아이콘만 있는 버튼은 접근 가능한 이름을 제공한다.
- 다크에서는 중성 밝은 CTA, 라이트에서는 신호색 또는 진한 중성 CTA를 사용할 수 있다.
- 색이 없는 ghost action도 hover·focus 상태가 분명해야 한다.

### 입력

- 라벨, 단위, 허용 범위, 오류 상태를 명확하게 표시한다.
- 숫자 입력은 모바일 키패드와 증감 조작을 고려한다.
- 자주 사용하는 값은 `1천`, `1만`, `10만` 같은 프리셋으로 제공할 수 있다.
- 슬라이더와 숫자 입력을 함께 쓰면 항상 같은 값을 나타내야 한다.
- 화면 상태와 계산 함수는 같은 정규화 규칙을 사용한다.
- 기본값과 프리셋을 제공하되 사용자가 모든 값을 수정할 수 있어야 한다.

### 결과

- 가장 중요한 결과를 첫 번째 시선 지점에 둔다.
- 월 비용, 요청당 비용, 사용자당 비용처럼 다른 단위를 계층적으로 구분한다.
- 비용 구성은 막대, 비율, 전후 비교 등 이해 가능한 시각화로 보조할 수 있다.
- 단순 숫자 나열보다 “가장 큰 비용 요인”과 “다음 조정 후보”를 설명한다.
- 동적 결과는 적절한 `aria-live`를 사용하되 과도한 낭독을 피한다.
- 값 변경 애니메이션 중에도 최종 수치를 즉시 읽을 수 있어야 한다.

### 카드와 패널

- 카드가 필요한 이유가 있을 때만 사용한다.
- 서로 관련된 입력은 하나의 패널로 묶고 모든 문장을 카드로 쪼개지 않는다.
- 강조 카드는 한 화면에 소수만 사용한다.
- 테두리, 배경색, 간격 중 최소한의 수단으로 구획한다.
- 다크 모드의 key surface와 라이트 모드의 flat surface는 같은 컴포넌트 역할을 유지해야 한다.

### 표와 비교

- 수치 단위, 공식 출처, 검증 날짜를 표시한다.
- 모바일에서는 가로 스크롤, 열 축약, 비교 카드 전환 중 가장 이해하기 쉬운 방식을 선택한다.
- 중요한 차이는 색상만으로 전달하지 않는다.
- 공식 출처 링크를 관련 값 가까이에 둔다.
- sticky header를 사용할 때 화면을 과도하게 가리지 않는다.

## 11. 모션 시스템

모션은 “최신 AI 제품”의 감각을 주되 기능 이해를 돕는 경우에만 사용한다.

### 허용 모션

- 페이지 진입 시 핵심 영역의 짧은 fade·translate
- 입력 변경 시 결과 숫자와 비교 막대의 자연스러운 전환
- 카드·버튼의 얕은 hover·press 반응
- disclosure 열고 닫기
- 복사, 저장, 내보내기 완료 피드백
- 로딩 스켈레톤과 빈 상태 전환
- 모바일에서 결과 이동을 돕는 제한적 sticky action

### 기준

- 일반 UI 전환은 150~250ms를 기본으로 한다.
- 긴 히어로 모션도 600ms 이내에서 안정화한다.
- `opacity`와 `transform`을 우선해 layout shift를 피한다.
- 계산값이 바뀔 때 숫자 애니메이션이 정확한 값을 가리지 않아야 한다.
- `prefers-reduced-motion: reduce`에서 이동·반복 모션을 제거하거나 즉시 상태로 전환한다.
- 한 화면에 여러 종류의 모션 언어를 혼합하지 않는다.

### 금지 모션

- 무한 반복하는 대형 배경 애니메이션
- 스크롤을 방해하는 강제 장면 전환
- 계산할 때마다 크게 튀는 카드
- 색 번쩍임, 과도한 blur, 과한 spring
- 사용자의 포인터를 계속 쫓는 장식

## 12. 반응형 기준

- 모바일 소형: 360~479px
- 모바일 대형: 480~767px
- 태블릿: 768~1023px
- 데스크톱: 1024px 이상

모바일에서는 다음을 반드시 확인한다.

- 단일 열 읽기 흐름
- 44px 이상의 터치 영역
- 표, 코드, 긴 모델명의 넘침
- 고정 요소가 결과나 입력을 가리지 않는지
- 입력 키보드가 열렸을 때 핵심 컨트롤 접근 가능 여부
- 가로 스크롤이 페이지 전체에 발생하지 않는지
- 도트 비주얼이 텍스트 대비와 성능을 해치지 않는지
- 애니메이션 없이도 전체 흐름을 이해할 수 있는지

## 13. 접근성 기준

- 키보드만으로 주요 작업을 완료할 수 있어야 한다.
- 모든 상호작용 요소에 명확한 `focus-visible` 상태를 제공한다.
- 다크·라이트 모두에서 본문과 인터페이스 텍스트 대비를 확보한다.
- 오류는 색상 외에 문장과 연결 관계로 전달한다.
- 입력 라벨, 설명, 오류 메시지를 프로그램적으로 연결한다.
- 동적 결과 변화는 필요할 때 적절한 live region을 사용한다.
- `prefers-reduced-motion`을 존중한다.
- 도트·그래프·색상 반전은 정보 전달의 유일한 수단이 될 수 없다.
- 테마 전환 컨트롤은 접근 가능한 이름과 현재 상태를 제공한다.

## 14. 외부 UI 컴포넌트

shadcn/ui를 기본 골격으로 유지하고 Cult UI 같은 외부 컴포넌트는 사용자 흐름을 더 명확하게 만드는 경우에만 선별적으로 사용한다.

### 허용 범위

- 저장, 복제, 이름 변경, 삭제 같은 후속 행동을 묶는 compact toolbar
- 펼침과 접힘, 상태 전환, 로딩, 빈 상태처럼 맥락을 보존하는 미세한 애니메이션
- 삭제 확인, 상세 설명, 입력 보조를 위한 popover 또는 disclosure
- 비교 결과의 중요한 변화나 완료 상태를 짧게 강조하는 피드백
- 온보딩에서 첫 행동을 설명하는 제한적인 인터랙션

### 금지 범위

- 핵심 입력이나 결과보다 눈에 띄는 장식용 애니메이션
- 과도한 유리 효과, 커서 추적, 파티클, 자동 재생 배경
- 기존 Pickkit 반경, 색상, 간격, 타이포그래피를 우회하는 기본 테마의 무수정 사용
- Magic UI, Aceternity UI 등 여러 시각 라이브러리의 무계획한 혼합

외부 컴포넌트 코드는 프로젝트 안으로 가져온 뒤 Pickkit 토큰과 접근성 기준에 맞게 수정한다. 새로운 의존성을 추가하기 전에 기존 컴포넌트와 CSS로 같은 사용자 가치를 구현할 수 있는지 확인한다.

## 15. 구현 순서

전체 디자인 변경은 한 번에 전면 교체하지 않는다.

1. 기존 화면과 공통 컴포넌트를 조사한다.
2. 다크·라이트 토큰과 테마 전환 기반을 먼저 만든다.
3. 공통 버튼, 입력, 카드, 결과, 표 컴포넌트를 정리한다.
4. 대표 계산기 하나를 새 시스템으로 전환한다.
5. 데스크톱과 모바일에서 실제 렌더링과 핵심 흐름을 검증한다.
6. 홈 히어로와 도트 비주얼을 구현한다.
7. 검증된 패턴만 나머지 계산기에 확산한다.
8. 모션과 성능, reduced-motion을 마지막에 전수 점검한다.

정보 구조를 먼저 설계하고 장식은 마지막에 판단한다. 공통 컴포넌트를 우선 확장하며 페이지별 임시 스타일 복제를 금지한다.

## 16. PR 검증 기준

UI 변경 PR은 본문에 다음을 기록한다.

- 적용한 디자인 토큰과 공통 컴포넌트
- 정보 구조를 바꾼 이유
- 다크·라이트 화면 검증 결과
- 데스크톱·모바일 화면 검증 결과
- 키보드, focus, 대비, overflow, reduced-motion 결과
- 주요 상호작용의 변경 전후
- 성능 또는 layout shift 영향
- Preview URL 또는 스크린샷

시각 검증이 불가능하면 완료 처리하지 않고 한계를 명시한다.

## 17. 완료 조건

UI 작업은 아래를 모두 충족해야 완료다.

- 기존 기능과 계산 결과가 회귀하지 않는다.
- 다크·라이트 모드가 모두 완성된 화면으로 보인다.
- 360px 이상에서 핵심 흐름을 완료할 수 있다.
- 키보드, focus-visible, 레이블, 오류, 대비 기준을 통과한다.
- reduced-motion에서도 기능과 의미가 유지된다.
- 테마 전환 시 깜빡임과 layout shift가 없다.
- 공통 컴포넌트와 토큰을 사용하며 임시 스타일 복제가 없다.
- Preview와 production에서 실제 화면과 핵심 상호작용을 검증한다.
- `check`, 테스트, 타입 검사, production build와 `git diff --check`를 통과한다.

## 18. 관련 스킬과 도구

사용 가능한 환경에서는 다음을 우선 활용한다.

- shadcn/ui: 접근 가능한 UI 컴포넌트와 구성 패턴
- Cult UI: 상태·보조 인터랙션과 절제된 모션에 한정
- React best practices: 상태, 렌더링, 컴포넌트 구조 검토
- Next.js: App Router, 메타데이터, 성능, 테마 초기화, 접근성 구현
- agent-browser 또는 동등 도구: Preview와 production의 실제 화면·상호작용 검증

스킬이 없거나 사용할 수 없는 경우에도 이 문서의 기준은 완화되지 않는다. 코드, 렌더된 HTML, CSS, 반응형 규칙과 접근성 속성을 근거로 대체 검증하고 한계를 보고한다.
